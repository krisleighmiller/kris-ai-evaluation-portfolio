CPU-only semantic retrieval experiment

Can semantic search justify its cost?

Indexing a library is a technical achievement. Whether the search results help anyone is a different question.

System
Project Gutenberg corpus, Chroma vector storage, persisted HNSW index and SQLite metadata
Environment
CPU-only indexing, without a GPU
Question
Feasibility, resource cost, and usefulness for historical-language retrieval

What I investigated

I built a semantic retrieval system over approximately 9 GB of Project Gutenberg text. I wanted to know whether it could run without a GPU, how long ingestion and chunking would take, what the storage cost would be, and whether semantic matching would be useful across historical changes in vocabulary.

Scale and cost

The original processing ran continuously for more than a week, and the resulting Chroma store occupied approximately 125 GB. A later read-only inspection found roughly 9.76 million embedding records in a 384-dimensional collection, with an HNSW vector index and SQLite metadata storage.

A later rebuild for a Harbor benchmark took almost 18 hours on my laptop and parsed 240 works. That smaller run supported a narrow test suite, not a demonstration that the full library could be rebuilt cheaply or quickly.

The finding

The CPU-only system could build the index, but the tested retrieval did not solve the intended historical-language problem. In the case I investigated, it could not bridge “anxiety” and “fear” as needed to compensate for vocabulary differences in older texts.

For this use case, the time and storage investment did not produce useful enough retrieval. That does not establish that all semantic search fails. It establishes that this corpus, retrieval approach, and intended task did not justify the cost.

Why the negative result matters

Reporting only the database size would make the experiment look more successful and less informative. The useful engineering conclusion was the gap between a system that can be built and a system worth using.
