The personal continuity system is in daily use. Extending Hermes and developing a multi-user assistant are separate, ongoing projects.

The problem

AI tools could help with individual tasks, but the administrative work between those tasks still fell to the person using them: finding old conversations, moving conclusions into durable notes, remembering what had been decided, synchronizing devices, checking email, and reconstructing where a project stopped.

The system was designed to hold that thread without silently taking authority over the work.

What the working system combines

  • Searchable conversation archives across multiple coding-agent environments.
  • Local semantic retrieval for finding related work when the exact wording is unknown.
  • A portable Markdown vault as the durable, human-readable source of truth.
  • Mobile capture for recording decisions and ideas where they occur.
  • Cross-device and server synchronization.
  • Scheduled reporting and bounded maintenance tasks.
  • Written recovery procedures and explicit operational boundaries.

Information governance

I defined rules that keep the system useful without allowing automation to flatten important distinctions:

  • Current decisions remain distinct from historical conversations.
  • Ideas and proposals remain distinct from commitments.
  • Source links and provenance remain available for verification.
  • Automated tools may organize records but may not silently rewrite their meaning.
  • Private records remain private, and credentials are not stored as knowledge.
  • The person retains authority over consequential actions and corrections.

Research, integration, and verification

The work began by comparing existing search, memory, retrieval, synchronization, and agent tools before adding custom components. The working system was assembled from reusable tools where they fit, with custom rules and integration only where a demonstrated gap remained.

I tested retrieval boundaries, synchronization behavior, scheduled delivery, permissions, unattended maintenance, and recovery paths. Failures were preserved and diagnosed rather than folded into a clean success narrative.

Continuity Assistant: profile confinement in Hermes

Continuity Assistant extends the continuity work toward a multi-user assistant. A central development problem is giving each profile useful tools while confining its filesystem access to its assigned working tree. This is an operating-system and application-enforcement requirement, not an instruction asking the model to stay in a directory.

The specification treats administrators and ordinary users as the same kind of profile with different privileges. A profile’s trusted identity must determine its authority; caller-supplied paths, environment variables, cached state, or a different entry point must not silently grant broader access.

What the implementation must actually do

  • Preserve useful work inside the boundary. Navigation, search, file creation, editing, renaming, deletion, and supported execution must work inside the assigned tree. Disabling the tools or making everything read-only does not satisfy the requirement.
  • Enforce the boundary across execution paths. Native Hermes file operations, shells, interpreters, compiled programs, child processes, and background jobs must respect the same authority. Checking a path in one tool is not sufficient when another route can perform the operation.
  • Account for indirect access. Tests cover links, traversal, inherited and passed file descriptors, host-side helpers, service brokers, and profile selection or reuse. The relevant question is which real object an operation reaches, not whether a displayed path looks confined.
  • Distinguish enforcement from unrelated failure. An outside operation needs a meaningful positive control. A missing file, unavailable tool, ordinary permission denial, or broken fixture cannot be counted as proof that confinement worked.
  • Check both sides of the contract. Synthetic inside operations must produce their expected results, while independent checks confirm that outside targets and relevant metadata remain protected. Passing counts do not replace coverage of the actual requirement.

Evaluating whether detailed instructions govern the work

The development process also provides a direct test of agent reliability. I observe what the model does with an initial task, introduce explicit requirements and procedures, and then trace failures at finer granularity when those instructions do not govern the result.

For example, “test filesystem confinement” becomes a per-tool, per-operation test contract: distinguish a shell builtin from an external executable; test an interpreter’s direct filesystem APIs rather than merely launching it; exercise read and write roles separately; establish valid controls; and inspect the real outside target after the attempt. Likewise, completing an inventory does not establish that the inventoried operations are confined.

The project contract also keeps the original outcome intact across worker replacements and partial results. An agent cannot declare the phase complete by moving unmet requirements into a later phase. Independent acceptance requires execution of the written cases with expected and actual behavior, not a review of another agent’s completion summary.

These interventions let me examine whether additional specification changes behavior, which instructions are repeatedly lost or reinterpreted, and how much human correction remains necessary. For the evaluated model family and workflow, the practical result is that I would not entrust it with autonomous production development. That finding is scoped to the evaluated system, not all coding tools.

Development status: The personal continuity system is operational. Continuity Assistant’s full profile-confinement outcome remains unaccepted; partial implementation and passing subsets are not presented as a completed security boundary.
